日期：2026-11-14。目标：优先验证生成成功率，打通 DeepSeek 文本、GPT 图片、页面组件、截图、文档及 ZIP 的完整流程。

## 本轮结论

全新正式任务 **1/1 成功**，耗时 **754.6 秒（约 12 分 35 秒）**。样本为“聚合剪辑软件 / APP”，复用历史确认草案、功能输入和 seed，在全新输出目录运行；未使用失败任务的阶段缓存，未手动订正业务内容。这里的成功允许程序内的有限重试和自动页面修复，不代表每个物理 API 请求都一次成功。

程序交付门禁 `ready_for_delivery=true`、`findings=[]`。生成 27 张业务截图；说明书 PDF 32 页，代码 PDF 60 页，使用 LibreOffice 转换。ZIP 包含 5 个 DOCX/PDF/TXT 文件，4,894,461 字节，完整性检查通过。本轮没有制作新安装器，也没有做干净 Windows 安装验收。

**这只是一个样本，不能把 1/1 当作长期成功率承诺。** 此前修复前的三类任务首轮结果仍保留为 0/3；不能把两组不同版本的测试合并成同一成功率。

## 修复内容与证据

- OpenAI 兼容文本接口遇到 `finish_reason=length` 时，重新请求完整响应并增加 `max_tokens`，最多追加两次。增长采用两倍预算或至少增加 1024，默认增长上限 8192，可通过 `SOFT_LLM_MAX_OUTPUT_TOKENS` 设置。原始调用明确请求更高预算时保留其预算，此上限限制的是自动增长。
- 保留完整响应结束标记、JSON 解析及交付门禁。截断结果不会作为完整 JSON 使用，也不以模板或中间图代替正式成功。独立 Default Template 模式仍保持零 Token。
- 重试事件记录旧预算、新预算和次数；错误回调与 trace 会正确标记长度恢复仍将继续重试。取消任务不触发长度恢复。网络重试预算保持原有边界。
- 本轮产品定位请求由 1500 增至 3000、6000 后完成，成功响应报告输出 4272 Token；业务细节由 2100 增至 4200 后完成。这证明原先请求预算不足，凭据并非无效。
- 全部文本请求模型为 `deepseek-v4.1-flash`，包括前端页面和参考图样式提取；图片模型为 `gpt-image-2`，使用独立配置。未更改本机 API 明文配置。

## 仍需处理的事项

1. **速度**：本轮 23 次截断增加了请求、等待和用量。下一步应以当前结果为基线，针对 DeepSeek 的长结构化请求调整初始预算并比较完整任务耗时；当前只验证了恢复成功，没有证据证明整单已提速。不能用修复前几十秒即失败的任务与本轮成功耗时做提速对比。
2. **覆盖率**：尚未验证修复后游戏和后台管理类的全新整单，也未覆盖持续限流、图片上游长时故障及客户安装环境。
3. **版面与行业适配**：说明书第 3、31 页提取文本分别为 27、24 行，程序按字符量与业务内容综合判定通过，仍提示人工复核。剪辑 APP 的行业子类被标记为“移动文件下载管理APP”，行业匹配仍需改进。程序门禁通过不等于最终人工内容验收通过；这些质量专项按用户要求后置。
