# API 密钥有效性与生成失败原因核查

检查日期：2026-11-12（北京时间）。本次使用本机既有配置进行少量真实调用，没有修改密钥、网关、业务源码或质量门禁，也没有重新打包。

## 结论

当前已安装客户端的文本密钥有效，gpt-6-sol 已真实返回 HTTP 200 和有效 JSON；图片密钥通过受保护的模型列表鉴权。上次整单失败不能归因于这两把密钥失效。

项目目录还存在一套旧配置，使用 gpt-5.5，其密钥和网关均与客户端配置不同。本次该旧网关建立连接时超时，没有收到 HTTP 鉴权结果，因此只能确认连接失败，不能据此认定旧密钥无效。

本轮没有重新付费生成图片，图片生成能力不能仅凭模型列表确认。2026-11-10 的两个真实图片生成请求均成功，但不代表后续永远可用。日志和报告没有公开密钥、完整网关地址或账户余额；没有更换客户配置。

配置加载差异：桌面程序会按同目录配置文件的修改时间合并 production.json 和 desktop.local.json，并支持独立的 custom 供应商配置。本轮按该合并顺序检查项目配置与已安装客户端配置，客户端文本请求使用有效 custom 供应商配置。不要用项目目录旧配置的测试结果代替客户端结果。

## 失败原因证据

### 1. 已复现不完整 JSON，鉴权仍然成功

对医疗软件产品身份蓝图做两次诊断请求，使用相同业务主题和当前提示词生成函数，输出预算分别为 1500 和 4000。两次均 HTTP 200、finish_reason=stop、收到流结束标记，提取出的内容分别为 1912 和 2090 字符，但均停在 pages 数组后的逗号处，缺少最外层结束花括号，不能被 JSON 解析。

两次返回的 completion_tokens 分别为 993 和 1070，接口没有报告 length。单独增加 max_tokens 未解决这两次格式问题；现有证据不能把它定为“输出 Token 配额耗尽”，也不能确定是上游模型还是网关处理造成。

仅做离线诊断时，删除末尾多余逗号并补齐最外层花括号，两个响应均可解析，且包含要求的十个顶层字段。这一步没有写回生成任务、没有绕过门禁，也不代表内容质量和材料交付通过。

### 2. 格式失败具有波动性，不能把流式认定为根因

另按原失败任务保存的 feature_hint、confirmed_outline 和 seed 重建业务请求，并恢复 semantic_contract；使用相同蓝图提示词函数进行对照：

| 请求 | 输出预算 | HTTP / 结束原因 | 结果 | 耗时 |
|---|---:|---|---|---:|
| 重建原任务业务上下文，流式 | 1500 | 200 / stop | 原始 JSON 有效，scenario/positioning 存在 | 61.06 秒 |
| 同业务上下文，非流式 | 4000 | 200 / stop | 原始 JSON 有效，scenario/positioning 存在 | 62.84 秒 |

成功的流式请求已保存原始 SSE 事件：结尾花括号确实由接口传回，解析时没有出现无法解码的 SSE JSON 记录。上述对照同时改变了输出预算，不能用于独立评估流式/非流式的因果差异；两次通过也不能当成整单成功率或修复证明。

前两次诊断使用简短业务说明，后两次恢复已确认的完整业务上下文；并非四次完全相同输入的重复实验。结论限于“当前接口有能力返回完整蓝图，也观察到非完整格式响应”。

### 3. 本地解析器会使错误位置产生误导

蓝图和 PageSpec 解析器都先取第一个左花括号至最后一个右花括号。当模型漏掉最外层右花括号时，最后一个右花括号可能实际属于内部模块对象，截取后的数据进一步丢失后续数组结尾。

因此原始响应的“末尾没有结束”会表现为更早位置的 Expecting ',' delimiter。不能看到该报错就认定指定位置真的只缺一个逗号。当前 provider 还仅以 HTTP 成功和内容非空报告请求成功，没有在日常 trace 中保留 finish_reason、usage 和流结束完整性证据。

### 4. 上次页面链路还有独立长度冲突

2026-11-10 的教育样本页面返回 6326、7246 字符，超过 PageSpec 的 6000 字符限制；触发压缩修复后仍出现无效 JSON。页面正常预算 1600、修复预算 1200，但字符数与 Token 数并非一一对应。增加预算也可能继续超出页面字符限制，必须同时控制区域、表格行数与字段数量。

上次 65 个文本请求中的 4 个请求错误事件均为程序主动取消，而非密钥鉴权失败。本轮旧网关的连接超时属于另一套配置的现状，不能用来解释上次客户端配置下的全部失败。

## 下一阶段建议

1. 为生产请求补齐脱敏的响应结束原因、usage 和流结束证据，并先判断原始 JSON 是否完整，避免截取逻辑产生误导；对结构完整、字段齐全的有限语法问题设计可审计修复，继续执行原有业务和质量校验。
2. 针对蓝图和 PageSpec 采用模型/网关实际支持的结构约束，协调 Token 预算与 6000 字符限制；修复后复测原三个失败样本，分别记录首次和续跑成功数。仅更换密钥、拉长超时或关闭流式均没有足够证据保证解决。
3. 明确项目开发配置与客户端配置的用途；若需要继续使用旧网关，先排查其连接状态，再验证旧密钥，不擅自覆盖当前客户端可用配置。
