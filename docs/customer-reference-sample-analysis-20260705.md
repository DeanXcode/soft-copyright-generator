## 关键观察

1. 客户参考手册的截图不是单一后台模板换内容，而是先有明确产品体验形态，再围绕同一产品连续展开操作状态。
2. 软件生成不能只用一个“产品形态”枚举。当前客户输入里至少存在三层分类：
   - 软件大类：软著申请里的软件分类，例如应用软件、嵌入式软件、中间件、操作系统。
   - 产品/行业小类：当前下拉里的 15 类，例如 APP、游戏软件、教育软件、金融软件、医疗软件、地理信息软件、云计算软件、信息安全软件、大数据软件、人工智能软件、VR 软件、5G 软件、小程序、物联网软件、智慧城市软件。
   - 体验形态/终端范式：由软件名称、业务场景、软硬件环境和产品小类共同推断，不应固定为 4 种。例如手机 App、小程序、H5、桌面 Web 后台、专业指挥台、传统 Windows 客户端、工业 HMI/SCADA、GIS/地图系统、三维/BIM/VR 场景、数据驾驶舱、运维控制台、算法训练平台、嵌入式设备屏、命令行/服务型中间件管理台等。
3. 参考样本中观察到的体验形态示例包括：
   - 手机 App / 小程序：建筑施工、景区票务样本，截图有手机状态栏、底部导航、地图、列表、详情、订单、表单等真实移动端页面。
   - 专业桌面 Web / 指挥台：机载电气、无人机样本，截图有统一主题、地图画布、监测图表、弹窗、设备/航线/任务管理状态。
   - 传统 Windows 桌面软件：水文样本，截图有老式蓝色标题栏、密集表单、表格和标注气泡。
   - 业务后台管理系统：设备、故障、用户、历史数据等页面沿着同一信息架构展开。
4. 手册页数通常约 13-26 页，截图约 10-23 张；源码材料基本保持 60 页连续代码；TXT 信息表多为 16 个软著字段。
5. 参考样本的真实感主要来自“产品连续性”：登录页、首页、列表、详情、弹窗、统计、设置等页面属于同一个视觉系统和同一套业务对象，而不是每个模块页套一张新组件模板。

## 当前生成链路的问题

当前链路虽然已经按行业给模块页分配 `admin_map`、`admin_pipeline`、`admin_form` 等角色，但本质上仍是规则渲染器在生成 HTML 组件拼贴。它能减少完全一样的后台壳，却很难达到参考样本里的“真实软件截图”效果。

根因不是 CSS 不够丰富，而是缺少两个上游阶段：

- 分类语义拆分：先区分软件大类、产品/行业小类、体验形态/终端范式，不能把三者混成一个枚举。
- 视觉稿生成：先生成一套统一的信息架构、页面流和视觉系统，再把页面实现成截图，而不是直接从模块名渲染截图。

## 推荐新链路

建议将正式生成链路改为：

```text
软件名称/补充说明
  -> 产品文档（软件大类/产品小类/PRD/信息架构/页面清单/数据对象/操作流）
  -> 视觉稿规格（体验形态、终端范式、设计系统、页面线框、组件状态、截图脚本）
  -> 可运行 UI 原型（HTML/CSS/JS 或前端项目）
  -> 截图
  -> 说明书正文按截图反写操作说明
  -> 源码材料按产品对象和页面流生成/抽取
```

其中“根据图写代码和手册”可以落地为“根据视觉稿规格生成可运行 UI 原型和截图，再让说明书消费截图清单、页面动作、字段和状态”。不建议让模型只输出一张不可编辑图片后再反向写代码；那样难以保证源码、截图、说明书和 TXT 一致，也不方便做自动门禁。

## 下一步落地建议

1. 新增 `product_experience_spec` 阶段：由 GPT 根据软件名、软件大类、产品/行业小类、运行硬件环境生成体验形态、目标终端、页面地图、页面流、核心数据对象、截图清单和视觉风格。
2. 新增视觉稿/原型生成器：按 `product_experience_spec` 选择可扩展的体验 shell，不再固定为四类或统一 `admin` shell；首批可落地移动端、小程序/H5、桌面 Web、传统 Windows、专业指挥台/GIS/工业监控等常见范式，后续继续扩展。
3. 修改说明书生成：说明书第四章不再按模块模板写，而是按截图清单中的页面动作写“用户进入页面 -> 点击/填写 -> 系统反馈”的操作说明。
4. 增加门禁：检查截图形态是否与 TXT 运行硬件环境一致，例如“安卓手机 分辨率 1280×720”必须生成移动端截图；检查页面清单是否覆盖登录、首页、列表、详情、表单/弹窗、统计/设置等真实产品状态。
